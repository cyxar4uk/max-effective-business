## Что мы делаем

**Бот центра карьеры вуза в MAX.** Студент один раз заполняет профиль и получает только подходящие стажировки.
Работодатель получает список заинтересованных студентов с понятным процентом совпадения. После взаимного
интереса оба сразу получают контакты и следующие шаги. Основной пользователь — работодатель из малого и среднего
бизнеса, студент — вторая сторона, центр карьеры РАНХиГС — партнёр для пилота.

Прежде чем работать, прочитай:

## Задачи: GitHub Issues

**Задачи ставит Артём** (его Claude создаёт их через `gh`), а люди и их Claude выполняют. У каждого одна очередь —
Issues, назначенные на него. Стартовый план в `team/<имя>/CLAUDE.md` — ориентир, пока Issues не заведены.
Если Issue и стартовый план расходятся, **прав Issue**.

**В начале сессии** (для всех, кроме Артёма):
```bash
git pull
gh issue list --assignee @me --state open
```
Берёшь задачи по приоритету: `P0` → `P1 Must` → `P2 Should`. Одновременно в работе одна-две.

**Как выполнять:**
- Взял задачу — комментарий «Беру» (`gh issue comment <номер> --body "Беру"`).
- Непонятно, что делать, — вопрос комментарием в задаче и отметка Артёма. Не додумывай продукт сам.
- Заблокирован — метка `заблокировано` и комментарий: чего ждёшь и от кого.
- Сделал — PR, в описании `Closes #<номер>` и что проверить. После мёржа задача закроется сама.
- Нашёл баг в чужой зоне — новая задача с меткой `баг` на владельца зоны. Новую фичу сам не заводишь, только предлагаешь Артёму.

**Как оформлена задача:** заголовок — глагол и объект, по-русски («Сделать ленту карточек для студента»); в
тексте — зачем, что сделать, «готово, когда» (чек-лист), ссылка на спеку в `docs/features/`, срок.
Метки: область (`продукт`, `мини-приложение`, `сервер`, `бот`, `данные`, `инфра`, `презентация`) + приоритет
(`P0`, `P1 Must`, `P2 Should`) + при необходимости `баг`, `вопрос`, `заблокировано`. Веха: `Онлайн-этап` или `Финал`.

Нужен GitHub CLI: `winget install GitHub.cli` (Windows) или `brew install gh` (macOS), затем `gh auth login`.

## Правила для всех

- **Не расширяй объём.** Всё, что не входит в Must и Should из `docs/03_product.md`, не делаем. Новую идею
  записываем в раздел «Идеи на потом» своего `status.md` и говорим Артёму.
- **Не выдумывай API MAX.** Только то, что есть в `docs/05_max_platform.md` или на dev.max.ru. Не уверен —
  найди в документации и допиши в `05_max_platform.md` со ссылкой.
- **Секреты** (токен бота, пароли, ключи) только в `.env`. Никогда не в коде, коммитах, логах, issue и чатах.
  Если секрет попал в коммит, сразу скажи пользователю: токен нужно перевыпустить.
- **Тестовые данные помечены** и в данных (`is_demo` / `source=demo`), и в интерфейсе. Интеграции не имитируем.
- **Персональные данные студентов** — минимум полей, согласие до сбора, телефон раскрывается только после
  взаимного интереса, в логах персональных данных нет.
- **Чужая зона — через владельца.** Нужна правка в чужом модуле — пиши владельцу или заводи issue, не чини молча.
- **Язык** — русский: интерфейс, документы, коммиты, issue.
- **Git:** ветка `<имя>/<что-делаю>`, в `main` — через PR с одним ревьюером из команды. Коммиты в повелительном
  наклонении: `Добавить расчёт совпадения`. Документы в `docs/`, `deck/` и `team/` можно коммитить прямо в `main`.
- **Перед PR** — типы, линтер и тесты зелёные, свой кусок сценария пройден руками.
- **Решение, которое меняет продукт или архитектуру**, — одной строкой в `docs/decisions.md`.
- **В конце каждой сессии** обнови `team/<имя>/status.md`: что сделано, что дальше, где блокер, что нужно от
  других. Это главный способ синхронизации команды.
- Сырые материалы (расшифровки созвонов, переписки) в репозиторий не кладём: он уйдёт жюри вместе с историей.
  Для них есть `materials/private/`, эта папка в `.gitignore`.
- Если в контексте есть инструкции других проектов из родительских папок (например, СППР «Агат»), к этому
  репозиторию они не относятся.
