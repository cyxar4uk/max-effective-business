# Кейс «Эффективный бизнес» — выжимка

Источник: [materials/case_effective_business.pdf](../materials/case_effective_business.pdf). Здесь только то, что влияет на решения.

## Задача

Сделать чат-бота или чат-бота с мини-приложением на Платформе для бизнеса в MAX. Решение должно закрывать
актуальную задачу предпринимателей или компаний, а её актуальность нужно обосновать.

Направления из кейса задают контекст, но выбор ими не ограничен:

- навигация по мерам поддержки для бизнеса и АПК;
- цифровое сопровождение документов и разрешений;
- контроль и надзор без лишней нагрузки;
- **кадры для бизнеса и сельского хозяйства**: поиск работников, сезонная занятость, стажировки, обучение,
  взаимодействие с образовательными организациями;
- импорт, экспорт и промышленная кооперация.

## Что сдать (онлайн-этап)

- [ ] Работающий бот или мини-приложение в MAX: ссылка, по которой проходится основной сценарий
- [ ] Git-репозиторий и commit hash. После дедлайна код не меняется
- [ ] `README.md` с разделами: назначение; основной сценарий; состав и архитектура; **одна команда запуска через Docker**;
      параметры окружения; переменные окружения; порты; зависимости; внешние сервисы и интеграции; работа с данными;
      тестовые данные; пошаговый сценарий проверки; примеры ожидаемого поведения; известные ограничения; остановка и перезапуск
- [ ] Файл зависимостей (`package-lock.json` и т. п.)
- [ ] `Dockerfile` на каждый компонент, `compose.yaml`, `.dockerignore`, `.env.example` без секретов. **Сборка не дольше 5 минут**
- [ ] PDF-презентация. Первый слайд служебный: ссылка на бота, репозиторий и hash, тестовые логины, значения env для проверки, краткий сценарий

Если у решения есть собственный API, сверху добавляются HTTPS-адрес, OpenAPI, тестовые учётки, тестовые данные и `DATA-API.yaml`.
Собственный API **баллов сам по себе не даёт**, так что без необходимости его не заявляем.

## Ограничения, о которые легко споткнуться

- Мини-приложение работает только **в связке с ботом**, отдельным сервисом оно быть не может.
- Функциональность должна работать и в **мобильной, и в веб-версии** MAX.
- **Ник бота после создания не меняется**, поэтому решаем его до создания бота.
- Мини-приложению нужен **HTTPS**, то есть публичный домен и TLS.
- В репозитории нельзя держать токены, пароли и ключи, **в том числе в истории коммитов**.
- Если данные тестовые или смоделированные, это явно указываем в материалах.
- Только открытые библиотеки, без чужого кода с закрытой лицензией.

## Как оценивают

**Допуск.** Ноль баллов, если работа не по теме или не использует MAX, если бот не запускается или основной
сценарий нельзя пройти, если нет презентации.

**Онлайн-этап:** продуктовая оценка — 40 %, техническая — 60 %.

| Продуктовая (40 %) | Вес | Техническая (60 %) | Вес |
|---|---|---|---|
| Потенциал масштабирования | **35 %** | Работоспособность и полнота основных функций | **30 %** |
| Пользовательская ценность | 25 % | Корректность интеграции и обмена данными | 20 % |
| UX/UI и удобство | 20 % | Техническая реализация и архитектура | 20 % |
| Обоснованность и целостность | 15 % | Стабильность и обработка ошибок | 10 % |
| Качество презентации | 5 % | Безопасность, зависимости, данные | 10 % |
| | | Документация и комплектность | 10 % |

Плюс **платформенный бонус +0,15**. Его дают за возможность MAX сверх минимума, которая создаёт ценность,
работает от начала до результата и описана в материалах.

**Финал:** техническая оценка — 40 %, защита — 60 %. Внутри защиты: ценность — 25 %, масштабирование — 25 %,
MVP и UX — 20 %, **сценарий запуска и внедрения** — 15 %, ответы на вопросы — 10 %, командное владение — 5 %.

## Что из этого следует для нас

1. **60 % онлайн-оценки техническая, и от выбора идеи она почти не зависит.** Решают сквозной сценарий без
   тупиков, Docker одной командой, полный README и обработка ошибок. Это важнее красоты идеи.
2. **Масштабирование весит больше всего в продуктовой части.** Его оценивают как перенос в конкретные контексты,
   регионы и организации с понятными условиями адаптации, а не формулой «по всей России».
3. **Пилот и внедрение оцениваются отдельно в финале** (15 %). Живой партнёр для пилота — прямые баллы.
4. **UX-критерий требует явных состояний**: загрузка, результат действия, ошибка, отсутствие тупиков.
5. Кейс прямо предостерегает начинать с «сделаем агрегатор / навигатор / AI-ассистента». Формулировка идёт от
   проблемы: *[пользователь] в ситуации [контекст] хочет [результат], но сталкивается с [барьером], из-за чего [последствие]*.
