## Состав и архитектура

| Компонент | Что делает | Технологии | Где |
|---|---|---|---|
| Мини-приложение | экраны студента и работодателя внутри MAX | React, TypeScript, Vite, MAX UI, MAX Bridge | `apps/miniapp/` |
| Сервер | API мини-приложения и бот в одном процессе | Node.js 24, TypeScript, Express 5, TypeORM | `apps/server/` |
| БД | пользователи, анкеты, стажировки, отклики, уведомления | PostgreSQL 18 | том `db-data` |
| Caddy (прод) | HTTPS с автоматическим сертификатом, маршрутизация | Caddy 2 | `deploy/Caddyfile` |

```
MAX (клиент) ──> мини-приложение ──HTTPS /api──> server ──> PostgreSQL
                                                   │  ▲
MAX Bot API  <── уведомления ── модуль bot <─ события ┘  └── вебхук /bot/webhook <── MAX Bot API
```

Внутри сервера модули разделены: `api` (маршруты, права), `auth` (проверка подписи MAX), `db` (схема и миграции),
`matching` (расчёт совпадения, чистые функции), `bot` (MAX Bot API и очередь уведомлений). API публикует внутренние
события (`internship.created`, `interest.created`, `interest.invited`), бот на них подписан: API ничего не знает про
Bot API, бот — про HTTP. Контракт API — [docs/api.md](docs/api.md), деплой — [docs/deploy.md](docs/deploy.md).

### Расчёт совпадения

Модуль [`matching`](apps/server/src/matching/match.ts) — чистые функции без БД и сети, покрыты юнит-тестами.
Никакого ИИ: работодатель видит, из чего сложился процент.

1. **Жёсткие фильтры.** Студенту должен подходить формат работы (очно, гибрид, удалённо). Для очных и гибридных
   стажировок город студента должен совпадать с городом стажировки (без учёта регистра, лишних пробелов и «ё»).
   Не прошёл фильтр — стажировка не показывается в ленте и не присылается ботом.
2. **Процент:** `70 % × доля закрытых обязательных навыков + 30 % × доля закрытых желательных`.
   Нет желательных — считаются только обязательные; нет обязательных — только желательные. Навыки сравниваются
   только по справочнику, свободный текст не участвует. Округление до целого, половина — вверх.
3. **Расшифровка** всегда идёт вместе с процентом: какие обязательные и желательные навыки закрыты, какие нет.
4. **Порог уведомления** — `MATCH_NOTIFY_THRESHOLD`, по умолчанию 60 %.

**Пример из тестовых данных.** Стажировка «Стажёр-аналитик продаж»: обязательные — Excel, SQL; желательные —
Power BI, Статистика. Студент знает Excel, SQL, Power BI, Google Таблицы.
Обязательные закрыты 2 из 2, желательные 1 из 2: `70 × 2/2 + 30 × 1/2 = 85 %`.

```json
{ "score": 85, "mustMatched": ["excel", "sql"], "mustMissing": [], "niceMatched": ["power_bi"], "niceMissing": ["statistics"] }
```

### Бот

Модуль [`bot`](apps/server/src/bot/) работает в том же процессе, что и API.

- **`/start`** — приветствие и две кнопки `open_app`: «Я студент» и «Я работодатель». Они открывают мини-приложение
  с параметром запуска `student` или `employer`. Диплинк `https://max.ru/<ник_бота>?start=internship_<id>`
  добавляет кнопку «Открыть стажировку». На любое другое сообщение бот отвечает подсказкой с теми же кнопками —
  тупиков в диалоге нет. В группах и на сообщения других ботов бот молчит.
- **Уведомления по событиям:**

  | Событие | Кому | Что |
  |---|---|---|
  | опубликована стажировка | студентам, прошедшим фильтры, с совпадением от порога | название, компания, процент, до трёх совпавших навыков, кнопка «Открыть» |
  | студент нажал «Интересно» | владельцу стажировки | «новый заинтересованный студент», процент, кнопка «Кандидаты» |
  | работодатель пригласил | студенту | контакт работодателя и чек-лист следующих шагов |
  | работодатель пригласил | работодателю | имя и телефон студента |

- **Очередь отправки** в таблице `notifications`. Все сообщения, включая ответ на `/start`, идут через неё:
  - лимиты MAX: не больше 2 сообщений в секунду в один диалог и 25 запросов в секунду всего (лимит платформы — 30);
  - временная ошибка (429, 5xx, сеть) — повтор с паузой 5, 10, 20… секунд, до 5 попыток;
    `403` (пользователь остановил бота) — без повторов;
  - у каждого уведомления ключ идемпотентности: повтор события или повторная доставка вебхука не присылают
    сообщение второй раз;
  - ошибка отправки не влияет на действие пользователя в мини-приложении: очередь работает отдельно от API;
  - в логи попадают только id и вид уведомления, без текста.
- **Тестовым пользователям бот не пишет**: у них выдуманные id MAX.

## Запуск одной командой

```bash
cp .env.example .env    # заполнить MAX_BOT_TOKEN и POSTGRES_PASSWORD

```

Поднимаются `db` и `server`; при старте сервер применяет миграции и (при `SEED_DEMO=true`) загружает тестовые данные.
Проверка: `curl http://localhost:3000/api/health` → `{"status":"ok","db":"ok"}`.

## Внешние сервисы и интеграции

| Сервис | Для чего | Как подключено | Статус |
|---|---|---|---|
| **MAX Bot API** (`https://platform-api2.max.ru`) | ответы бота и уведомления | `GET /me` — ник бота для кнопок; `POST /messages?user_id=` — отправка; заголовок `Authorization: <токен>`. | **Вебхук MAX** | входящие события бота (`bot_started`, `message_created`) | `POST /bot/webhook`, секрет в заголовке `X-Max-Bot-Api-Secret`; при ошибке MAX повторяет доставку, обработчик идемпотентен | реальная интеграция |
| **MAX Bridge** | мини-приложение внутри MAX: данные запуска, номер телефона | `window.WebApp`; подпись `initData` проверяется на сервере на каждом запросе | реальная интеграция |

## Работа с данными

**Что храним** (схема — [миграция](apps/server/src/db/migrations/1790000000000-Init.ts)):

| Данные | Зачем | Кто видит |
|---|---|---|
| id пользователя MAX, имя, фамилия, ник | вход без регистрации | сам пользователь |
| согласие на обработку ПД: дата и версия текста | обязательное условие до сбора анкеты | сам пользователь |
| телефон — только подтверждённый подписью MAX (`requestContact`) | связь после взаимного интереса | работодатель — **только после приглашения** |
| анкета студента: вуз, курс, направление, город, форматы, навыки из справочника | расчёт совпадения | работодатель — только у студентов, откликнувшихся на **его** стажировку |
| профиль компании, стажировки | публикация и подбор | все пользователи |
| отклики со статусом и процентом совпадения | воронка «интерес → приглашение» | студент и владелец стажировки |
| журнал уведомлений | повторы и отладка доставки | только сервер |

**Как защищаем:**
- каждый запрос к API подписан MAX (`initData`, HMAC-SHA256 токеном бота), подпись и срок проверяются на сервере;
- работодатель видит только свои стажировки и их кандидатов, чужие — 404;
- фамилия и телефон студента раскрываются работодателю только после приглашения;
- в логах нет `initData`, телефонов, заголовков и тел запросов;
- лимит запросов к API, CORS только для домена мини-приложения, секреты только в `.env`, история git проверяется
  на секреты в CI (gitleaks);
- БД не доступна из сети, в проде наружу открыт только HTTPS.

Тестовые записи помечены `is_demo = true` (стажировки — ещё `source = 'demo'`).

## Тестовые данные

**Все компании, стажировки и студенты в демо — вымышленные, подготовлены командой.** Совпадения с реальными
организациями и людьми случайны.

**Как загрузить:** автоматически при старте сервера, если `SEED_DEMO=true` (так по умолчанию в `compose.yaml`).
Вручную: `docker compose exec server npm run seed` или `npm run seed:demo` в `apps/server` при локальной разработке.
Повторная загрузка не создаёт дублей и не откатывает действия проверяющего: отклики, которые он уже изменил,
остаются как есть.

**Что внутри** ([`apps/server/src/seed/`](apps/server/src/seed/)):

| Что | Сколько |
|---|---|
| справочник навыков (не тестовые данные, грузится всегда) | 70 навыков в 11 группах |
| работодатели — малый и средний бизнес разных отраслей | 12 |
| стажировки: аналитика, маркетинг, финансы, право, HR и продажи, IT и дизайн; около половины удалённые | 26 |
| студенты РАНХиГС с разными навыками, городами и форматами | 36 |
| отклики со статусами «интересно», «приглашён», «отказ» | 59 |

Навыки студентов подобраны так, что у каждой стажировки есть подходящие кандидаты с совпадением от 80 %,
60–79 % и ниже 60 %, а часть студентов не проходит фильтры по городу или формату. Это проверяет тест
[`demo.test.ts`](apps/server/src/seed/demo.test.ts). Процент в откликах считает тот же модуль `matching`.

**Демо-отклики на стажировку проверяющего.** Проверяющий один, поэтому в демо-режиме на стажировку, которую он
опубликует в роли работодателя, сразу откликаются до 5 подходящих тестовых студентов с совпадением от порога.
Так список кандидатов не пустой, и сценарий можно пройти до приглашения.

**Как тестовые данные помечены:**
- в БД: `is_demo = true` у пользователей, анкет, компаний, стажировок и откликов; у стажировок ещё `source = 'demo'`;
- id пользователей MAX отрицательные — не пересекаются с настоящими, бот им не пишет;
- телефоны вида `+7 000 000-XX-XX` — кода 000 в российской нумерации нет;
- в интерфейсе — пометка «тестовые данные».
