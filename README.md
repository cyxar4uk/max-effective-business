## Состав и архитектура

| Компонент | Что делает | Технологии | Где |
|---|---|---|---|
| Мини-приложение | экраны студента и работодателя внутри MAX | React, TypeScript, Vite, MAX UI, MAX Bridge | `apps/miniapp/` (в `compose.yaml` подключается вместе с ним) |
| Сервер | API мини-приложения и бот в одном процессе | Node.js 24, TypeScript, Express 5, TypeORM | `apps/server/` |
| БД | пользователи, анкеты, места, отклики, уведомления, справочники | PostgreSQL 18 | том `db-data` |
| Прокси (прод) | HTTPS, маршрутизация: свой Caddy (`compose.prod.yaml`) или уже работающий на сервере nginx/Caddy (`compose.proxy.yaml`) | Caddy 2 / nginx | `deploy/` |

```
MAX (клиент) ──> мини-приложение ──HTTPS /api──> server ──> PostgreSQL
                                                   │  ▲
MAX Bot API  <── уведомления ── модуль bot <─ события ┘  └── вебхук /bot/webhook <── MAX Bot API
```

Внутри сервера модули разделены: `api` (маршруты, права), `auth` (проверка подписи MAX), `db` (схема и миграции),
`matching` (расчёт совпадения, чистые функции), `bot` (MAX Bot API и очередь уведомлений). API публикует внутренние
события (`internship.created`, `interest.created`, `interest.invited`), бот на них подписан: API ничего не знает про
Bot API, бот — про HTTP. Модуль `seed` при старте грузит справочники навыков и тегов задач, а при `SEED_DEMO=true` —
тестовые данные. Схемы компонентов, сценария и данных — [docs/architecture.md](docs/architecture.md), контракт API —
[docs/api.md](docs/api.md), деплой — [docs/deploy.md](docs/deploy.md).

Сервер — внутренний бэкенд мини-приложения: без подписи MAX его не вызвать. Собственный публичный API не заявляем,
поэтому OpenAPI и `DATA-API.yaml` не прикладываем.

### Расчёт совпадения

Модуль [`matching`](apps/server/src/matching/match.ts) — чистые функции без БД и сети, покрыты юнит-тестами.
Никакого ИИ: работодатель видит, из чего сложился процент.

1. **Жёсткие фильтры.** Студенту должен подходить формат работы (очно, гибрид, удалённо). Для очных и гибридных
   стажировок город студента должен совпадать с городом стажировки (без учёта регистра, лишних пробелов и «ё»).
   Не прошёл фильтр — стажировка не показывается в ленте и не присылается ботом.
2. **Процент:** `70 % × доля закрытых обязательных навыков + 30 % × доля закрытых желательных`.
   Нет желательных — считаются только обязательные; нет обязательных — только желательные. Навыки сравниваются
   только по справочнику, свободный текст не участвует. Округление до целого, половина — вверх.
3. **Расшифровка** всегда идёт вместе с процентом: какие обязательные и желательные навыки закрыты, какие нет.
4. **Порог уведомления** — `MATCH_NOTIFY_THRESHOLD`, по умолчанию 60 %.

**Пример из тестовых данных.** Стажировка «Стажёр-аналитик продаж»: обязательные — Excel, SQL; желательные —
Power BI, Статистика. Студент знает Excel, SQL, Power BI, Google Таблицы.
Обязательные закрыты 2 из 2, желательные 1 из 2: `70 × 2/2 + 30 × 1/2 = 85 %`.

```json
{ "score": 85, "mustMatched": ["excel", "sql"], "mustMissing": [], "niceMatched": ["power_bi"], "niceMissing": ["statistics"] }
```

### Бот

Модуль [`bot`](apps/server/src/bot/) работает в том же процессе, что и API.

- **`/start`** — приветствие и две кнопки `open_app`: «Я студент» и «Я работодатель». Они открывают мини-приложение
  с параметром запуска `student` или `employer`. Диплинк `https://max.ru/<ник_бота>?start=internship_<id>`
  добавляет кнопку «Открыть стажировку». На любое другое сообщение бот отвечает подсказкой с теми же кнопками —
  тупиков в диалоге нет. В группах и на сообщения других ботов бот молчит.
- **Уведомления по событиям:**

  | Событие | Кому | Что |
  |---|---|---|
  | опубликовано место | студентам, прошедшим фильтры, с совпадением от порога | название, компания, процент, до трёх совпавших навыков, кнопка «Смотреть» |
  | студент нажал «Интересно» | владельцу стажировки | «новый заинтересованный студент», процент, кнопка «Кандидаты» |
  | работодатель пригласил | студенту | контакт работодателя и чек-лист: для практики — направление, договор о практической подготовке (приказ № 885/390), задание, отзыв; для стажировки и подработки — задачи, график, оплата, оформление |
  | работодатель пригласил | работодателю | имя и телефон студента |

- **Очередь отправки** в таблице `notifications`. Все сообщения, включая ответ на `/start`, идут через неё:
  - лимиты MAX: не больше 2 сообщений в секунду в один диалог и 25 запросов в секунду всего (лимит платформы — 30);
  - временная ошибка (429, 5xx, сеть) — повтор с паузой 5, 10, 20… секунд, до 5 попыток;
    `403` (пользователь остановил бота) — без повторов;
  - у каждого уведомления ключ идемпотентности: повтор события или повторная доставка вебхука не присылают
    сообщение второй раз;
  - ошибка отправки не влияет на действие пользователя в мини-приложении: очередь работает отдельно от API;
  - в логи попадают только id и вид уведомления, без текста.
- **Не спамит:** студенту не больше 3 новых мест в сутки, остальные — одной подборкой со ссылкой на ленту;
  с 22:00 до 9:00 по Москве уведомления откладываются до утра. Ответ на `/start` и на сообщения приходит сразу.
- **Тестовым пользователям бот не пишет**: у них выдуманные id MAX.

## Запуск одной командой

```bash
cp .env.example .env    # заполнить MAX_BOT_TOKEN и POSTGRES_PASSWORD
docker compose up --build
```

Для проверки на своей машине подойдёт любое непустое значение `MAX_BOT_TOKEN` (например, `local-check`) и любой
`POSTGRES_PASSWORD`: API, подпись данных запуска для smoke-проверки и тестовые данные работают, бот только не
отправит сообщений. Проверка в самом MAX — через нашего развёрнутого бота, токен для этого не нужен.

Поднимаются `db` и `server`; при старте сервер применяет миграции, загружает справочники и (при `SEED_DEMO=true`)
тестовые данные. Проверка: `curl http://localhost:3000/api/health` → `{"status":"ok","db":"ok"}` или полная
smoke-проверка `node --env-file=.env scripts/smoke.mjs` (токен и порт берутся из `.env`; нужен Node.js 20.6+ на хосте;
создаёт служебного пользователя «Smoke»).

**Бот локально на `/start` не отвечает:** входящие сообщения MAX доставляет только на вебхук по HTTPS на 443 при
заданном `MAX_WEBHOOK_SECRET`, то есть на развёрнутом сервере ([docs/deploy.md](docs/deploy.md)). Локально бот только
ставит уведомления в очередь и пытается их отправить.

Сборка и запуск с нуля (без скачивания базовых образов) замеряются в CI на каждом изменении — workflow `compose`:
**28–34 с** на последних прогонах при лимите 5 минут.

### «Работа России»: что приходит и что будет, если сервис недоступен

- **Что берём.** Вакансии по запросам «стажёр» и «практикант» в Москве (пилот с РАНХиГС) и Татарстане (финал в Казани)
  из открытого API `GET https://opendata.trudvsem.ru/api/v1/vacancies/region/<код>`, все страницы до `meta.total`.
  В ленту попадают только места для студентов: без опыта или с опытом до года, с признаком студенческого места в
  названии («стажёр», «практикант», «младший», «помощник»…); продажа недвижимости «с обучением» — не берём.
  Город — из адреса вакансии; если его там нет, очное место не берём (кроме Москвы и других городов федерального
  значения): место в районе области не выдаём за место в столице региона. Удалёнка — по полю «тип занятости».
- **Как считается совпадение.** Навыки в вакансиях — свободный текст, поэтому название, требования и обязанности
  сопоставляются со справочником по словарю ([`skillMap.ts`](apps/server/src/import/skillMap.ts)). Вакансии, где не
  нашлось ни одного навыка из справочника, не берём: иначе совпадение было бы 100 % у всех.
- **Что храним.** Название, компанию, город, формат, обязанности и требования (до 1500 символов) и ссылку на оригинал.
  Телефоны, почту и контактное лицо **не храним** — ни из полей контактов, ни из текста обязанностей: студент
  откликается по ссылке на trudvsem.ru. В данных место помечено `source = 'trudvsem'`, это **не** тестовые данные.
- **Как часто.** При старте сервера (фоном, запуск не задерживает) и дальше раз в 6 часов. Пропавшие с сайта вакансии
  закрываются, но только если все запросы получены целиком.
- **Если сервис недоступен.** API отвечает медленно (12–15 с на страницу) и иногда обрывает ответ. На каждый запрос —
  таймаут 60 с, причины сбоев — в лог. Не ответила часть запросов — берём то, что пришло, ничего не закрываем.
  Не ответило ничего и в базе ещё нет мест из «Работа России» — заполняем её из сохранённого снимка
  ([`trudvsemSnapshot.ts`](apps/server/src/import/trudvsemSnapshot.ts), обновить: `npm run import:snapshot`). Если места
  уже есть, снимок их не трогает: не открывает закрытые и не затирает свежие данные старыми. Сценарий от сервиса не зависит.
- **Бот о местах из «Работа России» не уведомляет**: их много и они не от партнёров центра карьеры. Студент видит их в ленте.

## Работа с данными

**Что храним** (схема — [миграции](apps/server/src/db/migrations/)):

| Данные | Зачем | Кто видит |
|---|---|---|
| id пользователя MAX и имя; фамилия — только после согласия на обработку ПД; ник MAX не храним | вход без регистрации | сам пользователь |
| согласие на обработку ПД: дата и версия текста | обязательное условие до сбора анкеты | сам пользователь |
| телефон — только подтверждённый подписью MAX (`requestContact`) | связь после взаимного интереса | работодатель — **только после приглашения** |
| анкета студента: вуз, факультет, курс, направление, город, форматы, навыки из справочника (от 3), месяц практики (по желанию) | расчёт совпадения | работодатель — только у студентов, откликнувшихся на **его** место |
| профиль компании; места: тип, задача, навыки, теги задач, формат, город, сроки, оплата, число мест | публикация и подбор | все пользователи |
| отклики со статусом и процентом совпадения | воронка «интерес → приглашение» | студент и владелец стажировки |
| журнал уведомлений | повторы и отладка доставки | только сервер |

**Как защищаем:**
- каждый запрос к API подписан MAX (`initData`, HMAC-SHA256 токеном бота), подпись и срок проверяются на сервере;
- работодатель видит только свои места и их кандидатов, чужие — 404;
- фамилия и телефон студента раскрываются работодателю только после приглашения;
- в логах нет `initData`, телефонов, заголовков и тел запросов — в том числе в журнале ошибок прокси; логи Docker
  ротируются (10 МБ × 3);
- у работодателя не больше 20 открытых мест; некорректные запросы получают 4xx, а не 500;
- лимит запросов к API, CORS только для домена мини-приложения, секреты только в `.env`, история git проверяется
  на секреты в CI (gitleaks);
- БД не доступна из сети, в проде наружу открыт только HTTPS.

Тестовые записи помечены `is_demo = true` (места — ещё `source = 'demo'`).

## Тестовые данные

**Все компании, стажировки и студенты в демо — вымышленные, подготовлены командой.** Совпадения с реальными
организациями и людьми случайны.

**Как загрузить:** автоматически при старте сервера, если `SEED_DEMO=true` (так по умолчанию в `compose.yaml`).
Вручную: `docker compose exec server npm run seed` или `npm run seed:demo` в `apps/server` при локальной разработке.
Повторная загрузка не создаёт дублей и не откатывает действия проверяющего: отклики, которые он уже изменил,
остаются как есть.

| Что | Сколько |
|---|---|
| справочник навыков (не тестовые данные, грузится всегда) | 84 навыка в 12 группах |
| работодатели — малый и средний бизнес разных отраслей | 12 |
| места: аналитика, маркетинг, финансы, право, HR и продажи, IT и дизайн, маркетплейсы и сайт для малого бизнеса; около половины удалённые | 28 |
| студенты РАНХиГС с разными навыками, городами (Москва, Казань, Санкт-Петербург) и форматами | 40 |
| отклики со статусами «интересно», «приглашён», «отказ» | 65 |

Навыки студентов подобраны так, что у каждой стажировки есть подходящие кандидаты с совпадением от 80 %,
60–79 % и ниже 60 %, а часть студентов не проходит фильтры по городу или формату. Это проверяет тест
[`demo.test.ts`](apps/server/src/seed/demo.test.ts). Процент в откликах считает тот же модуль `matching`.

**Демо-отклики на стажировку проверяющего.** Проверяющий один, поэтому в демо-режиме на стажировку, которую он
опубликует в роли работодателя, сразу откликаются до 5 подходящих тестовых студентов с совпадением от порога:
до трёх сильных (от 80 %) и до двух, у которых чего-то не хватает, — чтобы была видна расшифровка. Среди тестовых
студентов есть жители Казани и Петербурга, поэтому очная стажировка не только в Москве тоже получит кандидатов.
Так список кандидатов не пустой, и сценарий можно пройти до приглашения.

**Как тестовые данные помечены:**
- в БД: `is_demo = true` у пользователей, анкет, компаний, стажировок и откликов; у стажировок ещё `source = 'demo'`;
- id пользователей MAX отрицательные — не пересекаются с настоящими, бот им не пишет;
- телефоны вида `+7 000 000-XX-XX` — кода 000 в российской нумерации нет;
- в интерфейсе — пометка «тестовые данные».
